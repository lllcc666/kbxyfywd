# 日常活动模块

本文件总结卡布西游常见“日常活动”类协议模式，不假设某个项目的文件结构。

## 常见类型

### 1. 简单发送型

特点：

- 直接发一个包
- 没有复杂状态机
- 可能无显式响应，或响应只用于成功判定

例子：

- 每日礼包
- 每周礼包
- 家族考勤

### 2. `open_ui` 查询型

特点：

- 先发 `open_ui` / `ui_info`
- 读取剩余次数、积分、勋章、冷却
- 再决定是否继续执行

例子：

- 深度挖宝
- 大多数周活动

### 3. 小游戏型

特点：

- 开始游戏
- 过程中可选同步
- 结束游戏提交分数或 `checkCode`

例子：

- 深度挖宝
- 跳舞大赛
- 各类活动小游戏

### 4. 分阶段型

特点：

- 同一 opcode 不同 params / protocolId 代表不同阶段
- 需要严格按状态推进

例子：

- 跳舞大赛
- 试炼活动

## 深度挖宝模式

常见流程：

1. `open_ui` 查询剩余次数
2. 发开始包
3. 收到 `sessionId`
4. 发结束包提交分数

分析时重点确认：

- 次数字段
- `sessionId`
- 分数字段
- 结束包 body 顺序

## 跳舞大赛模式

常见流程：

1. 进入活动或地图
2. 开始游戏
3. 过程同步
4. 结束
5. 退出阶段

分析时重点确认：

- 进入/退出是否走不同 opcode
- 过程包是否依赖 `serverTime` / `processid`
- 每日次数限制字段

## 试炼类模式

常见特点：

- 多个活动共用同一 opcode
- 通过 `params` 或 body 中的 `protocolId` 区分
- 结束时通常需要 `checkCode`

分析时重点确认：

- `checkCode` 公式
- 活动区分参数
- 奖励是结算还是兑换

## 排查顺序

当用户说“日常活动没完成 / 没奖励 / 次数不对”时：

1. 先找 `open_ui` 或等价查询响应。
2. 再找结束响应。
3. 看是否存在 `exchange`。
4. 看是否有每日次数或积分上限。
